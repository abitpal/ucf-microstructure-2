# BTC tradeability reproduction

The target is `TRADECHECK.json["BTC|0.1"]`: reported zero-baseline R² 0.03314587827676785, 44,284 selected trades, +0.65823 cents entry-cost mark-to-mid and -0.53478 cents crossed round trip. This is a historical reproducibility test, not a new untouched holdout.

Source: `notes/plan.md`, `scripts/tc.py`, and `TRADECHECK.json`. The saved VM `/var/lib/kalshi-study/scripts/tc.py` has SHA-256 `71d0759b5ecdee84aea147f1187b84a85b63a4a856faef11066ca218110beeda`, identical to the extracted script. The script uses 640 hidden units in the input layer plus five further 640-unit hidden layers; dropout 0.2; AdamW learning rate 0.001 and weight decay 0.3; OneCycleLR; up to 4000 steps; batch 1024; early stopping on 120 validation markets; seeds 11 and 23 averaged.

It trains one BTC model over multiple BTC 15-minute contracts, not one per contract. Last 30% of available BTC contracts by time are test, preceding 120 contracts validation, remainder train; train samples up to one million rows using numpy RNG seed 0. The target comes from a full-resolution midpoint tape, not the sampled feature panel. Data are pooled by rows and the `tc.py` training/evaluation weights are uniform rows. Historical result reports 219 features and 351 test markets.

Original per-market panels in `/mnt/data/panels/rich_BTC` are missing. The VM preserves 1,172 BTC midpoint tapes and `frame_rich.parquet`, but the latter has only 210 features and no timestamp, so it cannot exactly recreate the 219-feature, full-resolution-target experiment. A reconstructed sample panel had 219 features; the nine extra were four perp depth slopes, four perp liquidity-queue distances, and `size_imb_3`.

`azure_reproduction_driver.sh` rebuilds BTC 2026-09-15 through 2026-09-28 using `tools.panel_parallel --tier rich --perp-book --every 25 --workers 12`, the original VM modules, the Azure raw tape and scratch-only caches/panels. It requires 219 features and at least 1,000 panels matched to midpoint tapes, hashes each rebuilt panel and records source hashes, package versions and feature names. The reconstructed ticker list and R² must be compared with the historical results; regenerating from raw data does not guarantee byte-for-byte original inputs.

`reproduce_tc.py` is a minimally modified copy of `scripts/tc.py`. Besides explicit paths and fail-fast behavior when data are absent, it saves model checkpoints, normalization, feature order, market split, train sample indices and test predictions. It uses a separate output directory to avoid replacing the original reported JSON.

Azure run command: `pitch-btc-reproduction`, on `kalshi-analysis`. Status and logs: `/var/lib/kalshi-study/reproduction-btc-20261117/status.txt` and `run.log`. Panels and cache live on ephemeral `/mnt/scratch/reproduction` and will disappear on VM deallocation. On success, the job uploads `research/reproductions/btc-tradecheck-20261117/artifacts.tgz` to the private `tape` container for retrieval. The job must be monitored, and the VM returned to deallocated state after it finishes; it was deallocated before this task began.

To reduce elapsed time, `parallel_panel_replay.py` uses the same VM `tools.panel_parallel.one_market` implementation with 12 additional workers for September 25–28. It builds those dates in a separate scratch directory and hard-links only completed panels into the primary output without overwriting existing files. The original worker loop's `--resume` checks completed per-market files as it works. This changes scheduling, not model inputs or training; checksums are recorded after the primary build finishes. Monitor the separate managed command `pitch-btc-parallel` and `parallel.log` as well as the primary command before deallocating.

A bounded replay sanity check for `KXBTC15M-26SEP232000-00` matched 20,857 rows in the preserved historical frame. On finite row pairs, `k_imbalance_1`, `k_imbalance_3`, `rel_spread`, and `p_ret_1s` all matched within `rtol=1e-5, atol=1e-7`. Details and limitations are in `smoke_replay_validation.json`; this is not a full reproduction result.

The 219 ordered names from the one-market smoke replay are saved in `smoke_features.json`: 96 `k_` features, 107 `p_` features, 3 `xmkt_` features, and 13 unprefixed features. This is an observed sample schema; the full run discovers its feature union from 12 distributed panel samples and saves that list separately.

A local watcher (`watch_reproduction.py`) polls the managed Azure run and, upon success, downloads its private artifact archive to `research/reproduction_btc_20261117/` and writes `comparison.txt`. `watch_status.json` reports its state. The watcher deliberately does not deallocate the VM because other work may have begun there; inspect and deallocate it after all replay groups finish.

A second bounded helper, `parallel_middle_replay.py`, uses eight workers and the same non-overwriting completed-file handoff for September 21–24. Its separate run command is `pitch-btc-middle` and log `parallel-middle.log`. The primary run's per-market `--resume` continues to determine the final input set; these helpers do not change feature code or training math.
A subsequent check compared all 210 features shared with the preserved frame for the same market: all finite masks matched and all finite values were within the stated tolerance. This still says nothing about the nine additional features or other markets.

The VM also retains 1,205 BTC per-market files under `panel_big/`. For the checked contract, the old file has 20,857 timestamps exactly matching the rebuilt rich panel, but `scale_free` yields 107 features and only `size_imb_3` of the nine missing from `frame_rich`; the eight newer perp-ladder features are still absent. This collection is useful for validation and may support a separate ablation, but is not by itself the 219-feature reported dataset.

## Provisional fast reconstruction

`build_provisional_frame.py` assembles all 219 columns using the preserved 210-feature frame, timestamps and `size_imb_3` from the preserved `panel_big` files, and full-resolution midpoint tapes for all labels and mark-outs. It sets eight unavailable perp ladder columns to their observed inactive behavior. Across the first 331 rebuilt rich panels, four liquidity-distance columns were only zero/missing and four slope columns had no finite observations; that is not yet proof for the remaining markets. It checks counts for all 1,205 frame markets, compares two imbalance features row-wise for every included market, and `verify_provisional_frame.py` then verifies 211 non-assumed inputs and raw timestamps/mids/spreads bit-for-bit on 16 distributed rebuilt markets. Any mismatch aborts training. `provisional_tc.py` retains the original fitting and evaluation math, but uses the assembled frame and four Torch CPU threads instead of 12; the result must be labeled provisional until every raw panel is independently rebuilt and checked.

Azure command `pitch-btc-provisional` writes `provisional-status.txt`, `provisional.log`, and on success uploads the separate `provisional.tgz` artifact. The local watcher `watch_provisional.py` retrieves it to `research/provisional_btc_20261117/`. It does not replace the primary full replay.

During the provisional fit, the eight-worker middle-date helper was intentionally stopped to restore memory headroom; completed files were preserved. `pitch-btc-middle-resume` waits for the provisional run to reach COMPLETE or FAIL, removes only invalid interrupted files in the isolated secondary scratch folder, and resumes the same helper. The old `pitch-btc-middle` command may therefore show a nonzero exit by design. Before deallocation, inspect the resume command as well as the primary and late-date helpers.
